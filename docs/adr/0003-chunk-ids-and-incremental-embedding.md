# 0003. 내용 기반 청크 ID와 증분 임베딩

## 상황

위키 편집은 대부분 문서 일부만 바꾼다. 문서가 바뀔 때마다 모든 청크를 다시 임베딩하면 임베딩 서버(CPU면 특히)가 바로 병목이 된다.

## 결정

- 청크 ID는 `uuid5(doc_id + sha256(임베딩 입력) + 같은 내용의 순번)`로 만든다. 임베딩 입력은 `제목 > 섹션 경로` 한 줄과 본문이다.
- 임베더는 배치의 청크 ID로 Qdrant를 먼저 조회해서, 있는 청크는 저장된 벡터를 메시지에 그대로 싣고 없는 청크만 임베딩한다.
- 인덱서는 메시지에 모든 청크의 벡터가 있다고 가정한다. 임베더가 조회한 시점과 인덱서가 반영하는 시점 사이에 다른 판이 청크를 지웠어도 다시 넣을 수 있다.
- 청킹은 섹션 경계를 넘지 않는다. 고정 길이로 자르면 앞부분 한 줄만 고쳐도 뒤쪽 경계가 전부 밀려 모든 ID가 바뀐다(`tests/test_chunker.py`에 두 방식을 비교하는 테스트가 있다).

## 결과

- 섹션 하나를 고친 편집은 그 섹션의 청크만 임베딩한다. `kowiki_chunks_total{result="reused"}`로 절감량을 본다.
- 섹션 이름이 바뀌면 그 섹션 청크는 전부 다시 임베딩한다. 입력에 섹션 경로가 들어가기 때문이다.
- 모델이 바뀌면 벡터를 재사용하면 안 되므로 새 컬렉션 버전으로 재색인한다(재사용 조회도 그 컬렉션 기준이라 자연스럽게 전부 임베딩한다).
